Part 01Foundations

Introduction to Python

Why Do We Need Programming Languages at All?

Computers don't directly understand programming languages like Python, Java, C, or C++ — these languages are easy and human-understandable, but the machine only understands 0 or 1. A computer, at its core, is an electronic machine that only understands two states — ON and OFF, represented as 1 and 0. This is called binary or machine language.

Every single operation a computer ever performs — playing a video, opening WhatsApp, running an AI model — is, at the deepest level, millions of 1s and 0s moving through transistors on a chip.

Humans think in terms of goals and logic ("if the user is eligible, give a discount"), not voltages. Writing raw binary (called machine code) is:

  • Extremely error-prone (one wrong bit changes everything)
  • Impossible to read/maintain at scale
  • Not portable across different hardware

So, computer scientists built layers of abstraction:

  • Machine Language (1st Generation) — raw binary instructions specific to a CPU architecture (e.g., 10110000 01100001). Fast for the machine, unusable for humans.
  • Assembly Language (2nd Generation) — replaces binary opcodes with mnemonics like MOV, ADD, JMP. Still tied to hardware, but human-readable. A program called an Assembler converts it to machine code.
  • High-Level Languages (3rd Generation onward) — C, Java, Python, etc. Written in English-like syntax. A Compiler or Interpreter converts this into machine code.
Machine Code Example

Opcodes: 0001 → LOAD, 0010 → STORE, 0011 → SUB, 0100 → MOV, 0101 → ADD
For ADD R1, R2: ADD = 0101, R1 = 001 (3-bit), R2 = 010 (3-bit)
Machine code: 0101 001 010 (OPCODE + R1 + R2)

Why Python Specifically

Guido van Rossum designed Python (first released 1991) to prioritize readability and developer productivity over raw execution speed. The philosophy is captured in "The Zen of Python" — code should be simple, explicit, and readable almost like English pseudocode.

1.1 — What is Python?

Python is a high-level, general-purpose, interpreted programming language created by Guido van Rossum, with its first release in 1991 (Python 0.9.0) through the Netherlands-based research institute CWI. The language was named after the British comedy show "Monty Python's Flying Circus" — not the snake — reflecting the language's design philosophy of being fun and easy to use.

Python emphasizes code readability with its notable use of significant indentation instead of curly braces, which forces programmers to write clean, structured code that looks almost like pseudocode.

Python is classified as a multi-paradigm language because it supports procedural programming, object-oriented programming (OOP), and functional programming styles, all within the same language.

1.3 — Key Features of Python
  • Simple and Readable Syntax — Python code reads almost like English, reducing the learning curve for beginners.
  • Interpreted Language — Code is executed line-by-line by the Python interpreter (CPython by default); no separate compilation step is needed.
  • Dynamically Typed — Variable types are determined at runtime; you don't need to declare int x = 5, you simply write x = 5.
  • Interpreted AND Compiled (Hybrid) — Python source (.py) is first compiled into intermediate bytecode (.pyc) which is then executed by the PVM.
  • Object-Oriented — Everything in Python is an object, including functions, classes, and modules.
  • Extensive Standard Library — Often called a "batteries included" language.
  • Cross-Platform (Portable) — The same Python code runs on Windows, Linux, and macOS without modification.
  • Huge Ecosystem — Available via PyPI and installed using pip (e.g., NumPy, Pandas, Django, TensorFlow).
  • Free and Open Source — Distributed under the PSF license.
Compiled vs Interpreted — And Where Python Fits

This is one of the most commonly misunderstood concepts, so let's build it from first principles.

Compiled languages (e.g., C): The entire source code is translated into machine code (an .exe or binary) before execution, by a program called a compiler. Fast at run-time but requires a separate compilation step, and the binary is tied to the specific OS/CPU architecture.

Interpreted languages (e.g., pure Python conceptually): Source code is read and executed line-by-line, at run-time, by another program called an interpreter. No separate .exe is produced. More flexible but traditionally slower.

Critical Point — Python's Hybrid Model

Python is NOT purely interpreted. The standard Python implementation, CPython, first compiles your source code into an intermediate, lower-level, platform-independent format called bytecode (.pyc files), and then an interpreter called the Python Virtual Machine (PVM) executes that bytecode line by line. This is why Python is often called a "byte-compiled interpreted language."

1.5 — Python Program Execution Flow

Understanding how a Python program actually runs explains many behaviors — like why syntax errors are caught before the program starts, but runtime errors appear only during execution.

  • The programmer writes source code in a .py file (e.g., app.py).
  • The Python interpreter compiles it into bytecode (stored in .pyc files, usually inside __pycache__).
  • The Python Virtual Machine (PVM) executes this bytecode line by line.
  • If any error occurs during reading (syntax) or execution (runtime), the interpreter halts and displays a Traceback.
Real-World Analogy

Think of Python's execution like a live translator at a conference. A live translator (interpreter) converts the speaker's sentences one at a time as they speak, whereas a language like C uses a translator who translates the entire speech into a booklet (compiled executable) beforehand.

Detailed Execution Pipeline
[1] LEXICAL ANALYSIS (Tokenizer / Lexer) Breaks raw text into "tokens": keywords, identifiers, operators, literals │ ▼ [2] PARSING (Parser) Arranges tokens according to Python grammar rules into a Parse Tree Example: x = 10 ✓ correct, x == 10 ✗ incorrect (assignment vs comparison) │ ▼ [3] AST GENERATION (Abstract Syntax Tree) Simplified tree representing the logical structure of the program │ ▼ [4] COMPILATION TO BYTECODE AST → low-level, platform-independent instructions (LOAD_FAST, BINARY_ADD...) Saved/cached as .pyc files inside __pycache__ │ ▼ [5] PYTHON VIRTUAL MACHINE (PVM) A big loop (in CPython, written in C) that executes each bytecode instruction │ ▼ [6] OPERATING SYSTEM → [7] CPU → [8] MEMORY → [9] OUTPUT
Stage 1 — Lexer (Tokenizer)

The lexer reads your code letter by letter and groups them into small pieces called tokens.

tokenizer_example.py 
# Example: x = 5 + y becomes:
NAME(x)   OP(=)   NUMBER(5)   OP(+)   NAME(y)   NEWLINE

A computer can't understand raw text. It first needs to spot the basic pieces — just like you recognize words before understanding a full sentence.

If you write prin() instead of print(), the lexer doesn't complain. It just sees prin as a normal-looking identifier. The mistake gets caught later.

Stage 2 — Parser

The parser takes the tokens and checks if they follow Python's grammar rules. It builds a tree structure showing how the tokens fit together — like checking if an English sentence follows Subject-Verb-Object order.

If something breaks the grammar rules (like x = = 5), Python throws a SyntaxError right here — before your program even starts running.

Stage 3 — AST (Abstract Syntax Tree)

The tree from Stage 2 gets simplified into an AST — a cleaner tree that shows meaning, not just grammar.

= / \ x + / \ 5 y
see_ast.py 
import ast
print(ast.dump(ast.parse("x = 5 + y")))
Stage 4 — Compiling to Bytecode

Python's compiler turns the AST into bytecode — simple instructions made for the Python Virtual Machine (not your actual CPU).

see_bytecode.py 
import dis
dis.dis("x = 5 + y")

This bytecode gets saved in .pyc files inside a __pycache__ folder. Next time you run the same unchanged file, Python skips lexing, parsing, and compiling — it just loads the saved bytecode directly. That's why the second run is faster.

Stage 5 — The Python Virtual Machine (PVM)

This is the real "interpreter" — a loop written in C (the function _PyEval_EvalFrameDefault inside CPython) that reads bytecode one instruction at a time and does the matching low-level work: pushing/popping values, calling C functions for math, managing function calls, etc. This is why Python is called a "stack machine."

Stages 6–8 — OS, CPU, Memory

The PVM makes system calls to the OS for memory allocation, file I/O, screen output, etc. The OS passes these to the CPU which performs fetch-decode-execute cycles using registers and the ALU. Actual data manipulation happens in RAM and CPU registers, and the result flows to output (screen, file, network).

Walkthrough — What Happens with prin("Hello")?
✗ Wrong — Program 2

prin("Hello") — looks valid to the lexer and parser, but fails at runtime.

Text Token
prin IDENTIFIER
( LEFT_PAREN
"Hello" STRING literal
) RIGHT_PAREN

The lexer, parser, and compiler all succeed — prin is a valid identifier. Only at runtime, when the PVM executes LOAD_NAME prin, does it search every namespace in LEGB order (local → enclosing → global → built-in) and fail:

Scope (in search order) Result for 'prin'
1. Local variables Not found
2. Enclosing scopes Not found
3. Global namespace Not found
4. Built-in namespace Not found → NameError raised
error output 
NameError: name 'prin' is not defined
Stage prin("Hello") result
Lexing Succeeds — prin is a valid identifier token
Parsing Succeeds — matches valid call-expression grammar
Compilation Succeeds — bytecode is emitted without checking name existence
Runtime (PVM) Fails — NameError: name 'prin' is not defined
Key Insight

prin() fails with a NameError at runtime, not at compile time — because Python only checks whether a name actually exists when it tries to use it, not when it first sees it.

1.6 — Basic Structure of a Python Program
my_first_program.py 
# A simple program demonstrating Python's basic structure

def greet(name):
    """Return a greeting message for the given name."""
    return f"Hello, {name}! Welcome to Python programming."

if __name__ == "__main__":
    user_name = input("Enter your name: ")
    message = greet(user_name)
    print(message)
without_main_guard.py 
def greet(name):
    return f"Hello, {name}!"

user_name = input("Enter your name: ")
message = greet(user_name)
print(message)

Key observations:

  • No semicolons are required at the end of statements (unlike C, C++, Java).
  • Indentation (typically 4 spaces) defines code blocks instead of curly braces { }.
  • Comments start with # for single line, or triple quotes """ """ for multi-line docstrings.
  • if __name__ == "__main__": ensures the code runs only when the file is executed directly, not when imported as a module.

Part 02Landscape

Programming Languages

2.1 — What is a Programming Language?

A programming language is a formal set of instructions, syntax rules, and semantics that allows a human to communicate a sequence of computational steps (an algorithm) to a computer. Just as human languages have grammar rules, programming languages have strict syntax rules — a single misplaced symbol can prevent the entire program from running.

2.2 — Generations of Programming Languages
Generation Description Example
1GL — Machine Language Raw binary instructions (0s and 1s) directly executed by CPU 10110000 01100001
2GL — Assembly Language Uses mnemonic codes (ADD, MOV, SUB) instead of binary MOV AX, 5
3GL — High-Level Languages Human-readable, English-like syntax C, C++, Java, Python
4GL — Domain-Specific Designed for a specific purpose (databases, math) SQL, MATLAB
5GL — AI-Oriented Programmer specifies constraints and goals, not steps Prolog, OPS5
Real-World Analogy

Think of the generations like modes of communicating with a foreign chef. 1GL is drawing exact hand gestures for every micro-movement. 3GL (like Python) is speaking simple, structured sentences: "chop the onions, then boil the water." 4GL/5GL is simply saying "make me a pasta dish" and letting the chef figure out the steps.

2.3 — Low-Level vs High-Level Languages
Aspect Low-Level Language High-Level Language
Hardware Dependence Highly hardware-dependent (specific to CPU) Hardware-independent (portable)
Readability Difficult for humans to read Easy to read, close to English
Execution Speed Very fast, direct hardware control Comparatively slower (translation overhead)
Examples Machine code, Assembly Python, Java, C++, JavaScript
Typical Use Case Device drivers, firmware, embedded systems Web apps, mobile apps, data science
2.4 — Programming Paradigms

A programming paradigm is a fundamental style or approach used to structure and write code. Most modern languages, including Python, support multiple paradigms.

2.4.1 Procedural Programming

Code is organized as a sequence of instructions and reusable procedures/functions that operate on data. The program is divided into procedures/functions that perform specific tasks, executed one after another.

procedural_style.py 
# Procedural style: calculating area of a rectangle
def calculate_area(length, width):
    return length * width

area = calculate_area(5, 3)
print("Area:", area)
2.4.2 Object-Oriented Programming (OOP)

Code is organized around 'objects' that bundle data (attributes) and behavior (methods) together. Real-world example: modeling a Bank Account, where balance is data and deposit()/withdraw() are behaviors.

oop_style.py 
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount

account = BankAccount("Ayesha", 1000)
account.deposit(500)
print(account.balance)   # Output: 1500
2.4.3 Scripting Languages

A sub-category often used for automating repetitive tasks, gluing together other programs, and rapid development. Python, JavaScript, PHP, and Bash are commonly used as scripting languages — for example, automating the daily backup of a company's database at midnight.

2.5 — Compiled vs Interpreted vs Hybrid
Type How it Works Examples Trade-off
Compiled Entire source → machine code before execution C, C++, Rust, Go Fast execution, recompile for each platform
Interpreted Source → executed line-by-line at runtime Python*, Ruby, PHP Easier to debug, but slower execution
Hybrid Source → intermediate bytecode → VM interprets Python (CPython), Java, C# Balance of portability and performance

* Python is technically hybrid — CPython compiles source to bytecode (.pyc) first, then the PVM interprets that bytecode.

Part 03Debugging

Programming Errors & Debugging

3.1 — Why Study Errors?

Every programmer, no matter how experienced, writes code that fails on the first attempt. Studying the categories of errors systematically helps a developer quickly identify where a problem lies — whether it is a typo, a flaw in logic, or a condition that only appears during execution — and therefore fix it faster.

3.2 — Broad Categories of Errors
Error Type When Detected Description Real-World Analogy
Syntax Error Before execution (parse time) Violates the grammar rules of the language A grammatically incorrect sentence
Runtime Error (Exception) During execution Code is syntactically valid but fails when a certain condition is hit A recipe that fails because an ingredient is missing
Logical Error After execution (wrong output) Code runs without crashing but produces wrong results Following a recipe perfectly, but the result tastes wrong
Semantic Error Varies Statement is syntactically valid but means something different than intended Saying "I could care less" when you mean "I couldn't care less"
3.3 — Syntax Errors in Python

Syntax errors occur when the Python parser cannot understand a statement because it violates the language's grammar. Python detects these before running any part of the program.

syntax_error_example 
>>> if x > 5
  File "<stdin>", line 1
    if x > 5
           ^
SyntaxError: expected ':'

Common causes of syntax errors:

  • Missing colon (:) after if, for, while, def, class statements.
  • Mismatched or missing parentheses, brackets, or quotes.
  • Incorrect indentation (Python is strict about consistent indentation).
  • Using a reserved keyword as a variable name, e.g., class = "A".
3.4 — Runtime Errors (Exceptions)

Runtime errors, called exceptions in Python, occur while the program is executing, even though the code was syntactically correct. Python provides a robust built-in hierarchy of exception classes.

runtime_error_example.py 
# Simple average calculator for student marks
marks = [78, 85, 92, 0, 66]
total_students = 5

average = sum(marks) / total_students
print("Class Average:", average)

# If total_students is mistakenly set to 0:
# average = sum(marks) / 0
# --> ZeroDivisionError: division by zero

Common Python exceptions:

Exception Cause Example Trigger
ZeroDivisionError Dividing a number by zero 10 / 0
TypeError Operation on incompatible type "5" + 5
ValueError Right type, wrong value int("hello")
NameError Using an undefined name print(undeclared_var)
IndexError Index out of range my_list[10] on a 3-item list
KeyError Missing dictionary key my_dict["missing_key"]
FileNotFoundError File does not exist open("missing.txt")
AttributeError Method/attribute doesn't exist on object "hello".push()
ImportError Module not installed/found import numpyy
IndentationError Inconsistent indentation Mixing tabs and spaces
3.5 — Logical Errors

Logical errors are the most dangerous because the program runs successfully and produces output — but the output is wrong. There is no traceback or error message to point the programmer to the problem.

logical_error.py 
# Goal: Calculate the average of three exam scores
score1 = 80
score2 = 90
score3 = 70

# Logical error: forgot to divide by 3
average = score1 + score2 + score3
print("Average score:", average)   # Prints 240 instead of 80.0
Real-World Consequence

In 1999, NASA's Mars Climate Orbiter was lost because one team's software calculated thrust using imperial units (pound-seconds) while another team's software expected metric units (newton-seconds) — a classic logical/semantic error that cost the mission an estimated $327 million.

3.6 — Exception Handling: try, except, else, finally

Python provides structured exception handling so that a program can gracefully recover from runtime errors instead of crashing abruptly.

exception_handling.py 
def get_average_marks(marks_list):
    try:
        total = sum(marks_list)
        average = total / len(marks_list)
    except ZeroDivisionError:
        print("Error: The marks list is empty. Cannot compute average.")
        return None
    except TypeError:
        print("Error: The marks list contains a non-numeric value.")
        return None
    else:
        print("Average computed successfully.")
        return average
    finally:
        print("Average calculation attempt finished.")

print(get_average_marks([80, 90, 70]))
print(get_average_marks([]))

Explanation of each block:

  • try: the block of code that might raise an exception is placed here.
  • except: catches and handles a specific exception type; multiple except blocks can handle different errors.
  • else: runs only if the try block completed with no exception raised.
  • finally: always runs, whether an exception occurred or not — commonly used to close files or release resources.
3.8 — Debugging Techniques Used in the Real World
  • Reading the Traceback carefully — Python's error traceback shows the exact file, line number, and call sequence. Always read it bottom-up starting from the final error message.
  • Print/Logging Statements — Temporarily inserting print() statements (or, better, using the logging module) to inspect variable values.
  • Using a Debugger (e.g., pdb, or IDE breakpoints in VS Code/PyCharm) — Allows step-by-step execution and inspection without modifying code.
  • Rubber Duck Debugging — Explaining the code line-by-line out loud often reveals the logical flaw.
  • Unit Testing — Writing small, automated tests (using unittest or pytest) for individual functions.
  • Assertions — Using assert statements to state assumptions explicitly, e.g., assert age >= 0, "Age cannot be negative".
3.9 — Compile-Time vs Run-Time Errors
Aspect Compile-Time Errors Run-Time Errors
Detected By Parser/compiler, before program runs Interpreter, while program is executing
Program Execution Never starts Starts but terminates abruptly (unless handled)
Typical Examples Missing colon, unmatched brackets, bad indentation Division by zero, invalid index, missing file
Prevention Careful typing, IDE syntax highlighting Input validation, try-except blocks, defensive coding
3.10 — Best Practices to Minimize Errors
  • Always validate user input before processing it (e.g., check if a string can be converted to a number before calling int()).
  • Use meaningful variable and function names to reduce logical mistakes.
  • Break large problems into small functions — smaller units are easier to test and debug.
  • Use version control (Git) so a working version can always be restored.
  • Write test cases alongside your code, not after — this is called Test-Driven Development (TDD).
  • Never use a bare except: clause in production code — always catch specific exception types.
